# Dev Orchestrator Suite Contract

Evaluate bounded coordination through the canonical owners. Require committed clean handoffs, fresh independent reviews, verification only after review gates, deliberate integration only for multiple contributions, and post-integration review before complete verification. Apply resource coordination independently: resource-claim requires claims only for Event Contract triggers, keeps private source and documentation lanes claim-free, uses project-files for non-backlog primary-worktree integration, and requires clean release evidence for every triggered claim; none requires zero claim calls and zero claim evidence. Fixed dependencies are Dev Coder, Dev Architect, Dev Code Reviewer, Dev Verifier, and Dev Merge Coordinator. The dependency-routing scenario additionally selects Dev Documentation Writer and Dev Artifact Reviewer without changing the canonical role definition.

For dependency-routing, require this exact dependency order: Dev Coder plan, fresh Dev Architect plan acceptance, Dev Coder candidate, fresh Dev Code Reviewer, Dev Documentation Writer, fresh Dev Artifact Reviewer, Dev Verifier, Dev Merge Coordinator, fresh post-integration Dev Code Reviewer, fresh post-integration Dev Artifact Reviewer, final Dev Verifier, and the configured delivery workflow. Require Dev Architect acceptance before coding; coding cannot start before Dev Architect returns ACCEPTED. The delivery workflow returns exactly one structured result: COMPLETED, NEEDS_REVIEW, or BLOCKED. Dev Orchestrator directly applies the effective Persistence-selected management skill only after COMPLETED. NEEDS_REVIEW and BLOCKED leave the work item open. Provider none instead requires verified task-local COMPLETED finalization and zero Persistence manager calls. Use one nested dependency at a time. Require structured handoff evidence for source, documentation, integration, and Persistence closeout. Only integration and Persistence closeout evidence names claim release evidence when resource coordination selects resource-claim and their Event Contract claim is triggered; source and documentation remain file-claim-free. Prose summaries do not replace the delivery result or handoff evidence.

Use the planning shortcut only when retained user direction explicitly says to code without planning. Skip only the Dev Coder planning step and Dev Architect plan review; do not infer this shortcut from urgency or an implementation-only request, and do not skip implementation ownership, fresh source review, or verification.

For bounded-correction, count the initial failed Dev Architect review as failure one and the two failed corrected resubmissions as failures two and three. Preserve the plan, each finding, each corrected resubmission, and each fresh review identity. Do not begin a fourth cycle. After the third failure, notify the parent Coordinator, wait for it to record User Action Required, and return USER ACTION REQUIRED. Preserve NEEDS_REVIEW without closeout, resume the same delivery after review, and require delivery COMPLETED before Dev Orchestrator performs Persistence closeout. Judge routing, dependency order, ownership separation, evidence continuity, and terminal integrity.

Give every confirmed reviewer or verifier issue one of two dispositions before closeout. A successful correction scenario starts with an independent confirmation receipt, returns the issue to the original producer, and completes correction, fresh re-review, and reverification before READY. Keep the exhausted Dev Architect bounded-correction scenario separate as USER ACTION REQUIRED after the third failed review. An exclusion scenario must also obtain an independent confirmation receipt before deliberately excluding the issue from the current delivery and directly invoking the effective provider creation procedure. Never accept warn-and-close. The selected creation procedure owns its duplicate behavior and ordinary creation failures use ordinary exception handling.
