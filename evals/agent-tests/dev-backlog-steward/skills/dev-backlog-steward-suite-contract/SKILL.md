# Dev Backlog Steward Suite Contract

Evaluate ordinary durable typed lifecycle state through the effective Persistence-selected backend, while routing explicitly requested lightweight Future Ideas only through the file provider or an explicit one-item file override. A Future Idea has a title, Synopsis, Origin or Rationale, optional Notes or Revisit Trigger, no lifecycle fields, and the output contract backlog item, Future Idea, or status update. A non-file Future Idea operation without the override is BLOCKED and creates neither a provider issue nor a shadow file. Promotion preserves the idea with Promoted To and creates complete ordinary work whose Source Evidence contains the exact idea path, whose Completion is direct-main, feature-branch, or UNSET, and whose Open Questions section records agent-resolvable uncertainty or None. Treat promotion as a failure-atomic transaction under the serialized primary-main backlog claim: preflight target collisions; snapshot exact source and target bytes, target existence, and the exact full Git index file bytes and existence; stage only the reciprocal pair; use a path-limited commit that preserves unrelated staged state; and verify the confirmed commit contains exactly both paths. After a target-write, idea-write, validation, or commit failure, restore and verify the exact worktree and Git index snapshots. Restoration removes only a target created by that promotion attempt. If restoration cannot be completed or verified, report BLOCKED, retain the backlog claim, name the preserved recovery evidence and Dev Backlog Steward recovery owner, and do not report release or readiness. Holding accepts the underlying dispatchable Type or Type: Holding; User Action Required retains its underlying dispatchable Type. Directly requested or explicitly authorized ordinary items start Ready in their typed active queue. Status: Proposed is invalid. Ordinary items need source context, requirements, acceptance, dependencies, and verification; claimed or resumed items need visible exclusive ownership. Recovery must reconcile item, claim, logs, results, and verification before completion or archival. A blocked handoff commits Status: Blocked, Owner: Unowned, and Claim: None while retaining the exact blocker, unblock condition, evidence, and acceptance criteria, then releases prior ownership so both item and registry are unowned. Reject an unowned Blocked to Running shortcut even when the unblock condition is satisfied. Resumption records eligible Ready state, successful acquisition of a new claim, the new owner, and only then Running. A failed or absent claim must restore the exact pre-attempt Blocked bytes, keep the item unowned and not Running, and preserve all prior evidence. Reject GitHub issues for Future Ideas, shadow backlogs, state-implied ownership, unsupported status changes, lost history, or unrecoverable handoffs. Judge item or idea quality, ownership integrity, transition evidence, promotion provenance, recovery, evidence preservation, output completeness, and handoff completeness.
