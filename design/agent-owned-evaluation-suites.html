Governed behavioral evaluation

Agent-Owned Evaluation Suites

Each conceptual agent has an executable suite. The suite runs selected behavior, binds identity to retained evidence, applies exact checks, and uses an independent Judge.

Evidence boundary. A task label or diagnostic summary cannot prove a verdict. Exact receipts, digests, identities, dispositions, and cleanup evidence determine the result.

Suite anatomy

The common protocol and suite index control the catalog. Each named suite owns the participants, scenarios, and target-specific acceptance contract.

Control

Suite manifest

Hardcodes the supervisor, target, and Judge runtime names separately from portable role identifiers and generated adapter paths.

Behavior

Scenario catalog

One authoritative scenarios.yaml file derives a small set of high-value cases from the complete canonical agent definition.

Coordination

Supervisor

Coordinates one suite under the common protocol and keeps only one child active at a time.

Subject

Target agent

The standard generated agent performs the behavior under evaluation.

Judgment

Independent Judge

Returns the governed semantic disposition after required deterministic gates.

Acceptance

Contract skill

Defines the acceptance rules that apply to the target agent.

Catalog and coverage

Suites are ordered by descending direct end-user value. Existing catalogs and the runner remain the execution and evidence foundation during migration to the agent-owned layout.

A skill probe is a targeted diagnostic selected by an agent scenario. Skill probes are not the units used to plan exhaustive coverage.

Runtime identity

Codex project-agent names contain lowercase letters, digits, and underscores. Retained session evidence must prove that every child loaded the staged project-agent definition.

Task labels and final prose do not prove that identity.

Bounded runner

Execution has a controlled beginning and end

The runner validates the complete catalog, selects work, limits each batch, retains partial failures, records timing, and removes disposable state.

01 / VALIDATE

Validate the catalog

Check the complete suite catalog before selected execution.

02 / SELECT

Select suites and scenarios

Accept explicit suite and scenario selectors.

03 / BATCH

Bound parallel work

Group at most four ordinary supervisors in one coordinator batch.

04 / RETAIN

Keep failure evidence

Preserve partial failures and governed checkpoints.

05 / TIME

Record two clocks

Store UTC completion time and monotonic elapsed time.

06 / CLEAN

Remove isolated state

Remove disposable workspaces and isolated authentication state after each batch.

Explicit harness selection

Codex can prove more than Junie

Every reporting run selects Codex or Junie. Worker capacity depends on suite count, processors, available memory, and the repository ceiling of four.

Codex digest-bound

  • Binds generated TOML agent definitions by digest.
  • Can bind the Judge response to its session, parent, scenario order, rollout, extracted response, and output artifact.
  • Can support a governed terminal PASS or FAIL when every required receipt is valid.

Junie 2285.4 BLOCKED

  • Stages Markdown custom agents through an isolated lookup location.
  • Retains a path- and SHA-256-bound staged manifest.
  • Exposes agent identifier, name, STARTED and FINISHED states, and step identifier.
  • Does not expose the definition digest or parent relationship needed for exact attribution and topology acceptance.

Disjoint destinations. Every selected suite receives separate run, evidence, checkpoint, and report destinations.

Junie catalog guard. A full Junie catalog run requires the explicit allow-full-junie option. A selected smoke run does not require that authorization.

Receipt-driven outcomes

Evidence determines the verdict

Every configured deterministic check appears exactly once with catalog-matching criticality, an exact disposition, a retained path, and a SHA-256 digest.

PASS

Complete verified proof

Runner-verified receipts and the exact Judge disposition bind to the selected scenario checkpoint and retained artifacts.

FAIL

Governed negative result

Exact evidence proves the scenario failed its declared acceptance contract.

BLOCKED

Required proof is unavailable

Identity, topology, authority, runtime, or evidence limits prevent a valid passing claim.

Authorized Judge skip

The skip names the exact failed critical check and uses the skipped-critical-failure disposition.

Diagnostic summaries

Diagnostic text can remain visible in a report. It never proves a verdict.

Immutable publication

A report is an evidence package

Each suite generation stores self-contained HTML, machine-readable metadata, and a content-addressed evidence bundle in one immutable directory.

PACKAGE

Build one generation

Write only the selected suite generation and its stable manifest. Update aggregate counts and the suite's global entry deterministically.

RE-HASH

Reopen every object

Resolve checkpoint and identity roots, then re-hash receipts, bound artifacts, Judge rollout, extracted response, and output artifact.

BIND

Bind the manifests

Metadata and the stable suite manifest bind the evidence-manifest digest. The generation digest covers metadata, HTML, and evidence manifest.

VALIDATE

Validate before replacement

Validate the complete pending generation and bundled objects before replacing the stable manifest.

REBUILD

Validate again

Aggregate rebuild validates the same bundle before counting CURRENT PASS or FAIL.

EXPOSE

Keep bad inputs visible

Missing, mutated, stale, malformed, duplicate, incompatible-revision, and mixed-harness evidence remains non-passing.

Declared runtime capabilities

Exceptional facilities stay narrow

A scenario declares exceptional facilities through runtimeCapabilities. The runner supplies only the pinned inputs and local permissions that the selected case needs.

Offline Node

Matched dependency tree

The fixture receives only the selected project dependency tree after installed TypeScript matches the tracked lockfile.

Offline Maven

Checksum-pinned repository

The fixture receives only manifest-named repository files. The isolated home forces offline execution, and fixture tests pass before model execution.

Loopback and processes

Single-supervisor batch

The managed profile permits local binding, denies non-local destinations, and limits writes to the disposable workspace.

Browser

Fresh runner-owned state

Each interaction gets a fresh headless browser, context, page, and loopback fixture server with pinned Playwright and Chromium.

Two network barriers. Request interception blocks non-loopback HTTP and HTTPS. The managed permission profile independently denies non-local network access.

Target-authored interaction

Browser PASS proves the whole interaction

The target is the sole author and initiator. The runner owns preflight, broker authentication, bounded execution, retained runtime evidence, and cleanup proof.

Preflight failure. If Chromium cannot launch or observe the configured local page, the runner returns an infrastructure-blocked batch result before coordinator or target invocation. The runner retains preflight cleanup evidence.

Bounded interaction rules

  • The supervisor passes browser assignment fields without renaming or paraphrasing.
  • The broker validates the one-time token, scenario, exact paths, flat action schema, and both digests.
  • After validation succeeds, the broker launches Chromium outside the target command sandbox.
  • Validation failure removes stale validation evidence, leaves the one-shot broker available, and does not launch a browser.
  • The wrapper accepts user-visible Playwright locators and deterministic waits.
  • The wrapper does not accept arbitrary target evaluation or sleep actions.
  • A role name is an accessible name. Unlabeled alert or status content uses exact visible text.
  • Focus and accessibility-attribute observations can retain an intentionally seeded UX defect.

Runner-owned isolation

  • No Chrome channel, persistent profile, desktop browser, existing tab, or inherited authentication state.
  • Scenario evidence, broker identities, and ports have independent roots.
  • Browser-capable suites run as isolated single-supervisor batches.
  • Concurrent work cannot share browser context, profile, evidence, authority, or port state.
  • Unused brokers close after failure or interruption, and closure receipts remain retained.

Browser PASS evidence

  • Target-bound validation, runtime, and broker receipts
  • Trace, final screenshot, and target-requested screenshots
  • Console, browser request, and browser response events
  • Service route and status diagnostics
  • Playwright and Chromium versions
  • Broker, browser, context, and page identities
  • Fixture root and selected loopback ports
  • Interaction and receipt digests
  • Timestamped page, context, browser, fixture-server, and broker close receipts
  • Complete cleanup even when a route finishes BLOCKED

BLOCKED does not waive cleanup. The missing-runtime-evidence UX case remains a static-evidence BLOCKED path. The blocked-route-owned-cleanup case must still prove complete runtime cleanup.
