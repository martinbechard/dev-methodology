Shell Anatomy

The shell uses three navigation levels. Suite navigation moves across the whole documentation set. Document navigation moves through the reading sequence. Section navigation moves within the current page.

<body>
  <a class="skip-link" href="#main-content">...</a>
  <header class="site-header">...</header>
  <nav class="suite-nav" aria-label="Documentation pages">...</nav>
  <main id="main-content">
    <nav class="document-nav">...</nav>
    <section class="hero">...</section>
    <nav class="page-section-nav">...</nav>
    <section class="section">...</section>
  </main>
  <footer class="site-footer">...</footer>
</body>

Suite Navigation

Suite navigation is the global navigation for a related documentation set. It appears below the brand header and before the main-content sequence navigation.

Adopted pattern
Use on every page in a multi-page documentation suite.

The design-system pages demonstrate this pattern. The audited dev-methodology snapshot does not share it.

Illustrative navigation specimen. The labels and destinations are examples. A conforming page uses the target suite's authoritative navigation inventory.

Use links, not badges

Each pill is an anchor because it changes location. A badge only labels content and must not replace navigation.

Expose the current page

Add aria-current="page" to one link. Use color and border changes as supporting visual cues.

Keep labels stable

Use the same order and link names on every page. Do not shorten labels differently on narrow screens.

Wrap before scrolling

Let links wrap when the set is small. Use horizontal scrolling only when wrapping would create an excessively tall navigation block.

<nav class="suite-nav" aria-label="Documentation pages">
  <a href="index.html">Index</a>
  <a href="page-shell.html" aria-current="page">Page shell</a>
  <a href="content.html">Content</a>
</nav>

Design-system-owned pattern: all pages in design/documentation-design-system. Related source gap: the audited dev-methodology pages provide sequence and section navigation but no shared suite navigation.

Hero

A hero introduces the page between document navigation and section navigation. The default hero uses one content column.

Use the default hero for most documentation pages. It contains an optional eyebrow, one page title, and a short description of the page scope.

Two-Column Hero

Use a two-column hero when a compact card provides context that governs the whole page. Suitable content includes a principle, scope boundary, evidence limitation, or source snapshot.

Operating model

Documentation Lifecycle

The left column introduces the page and defines its scope.

Continuity

The right card states context that applies to the whole page.

  • Place the title column before the card in the document order.
  • Stack the card below the title column on narrow screens.
  • Use the default hero when the card would only repeat the description or add decoration.
<section class="hero hero--split" aria-labelledby="page-title">
  <div class="hero-copy">...</div>

</section>

Structural provenance: design/orchestrated-development-lifecycle.html uses a title-and-lede column with a core-principle card. Its typography remains a separate foundation variation.

Versioning And Compatibility

The design system uses Semantic Versioning. The current version is 0.1.1, which identifies a usable draft whose contracts may still change before 1.0.0.

Required
Every design-system page and every conforming document must identify the exact design-system version it follows.

Use the visible footer label for readers and the metadata value for tools. Both values must match the canonical VERSION file.

  • Major: increment for an incompatible change to adopted markup, tokens, behavior, accessibility requirements, or documented usage contracts.
  • Minor: increment for a backward-compatible component, pattern, token, or capability.
  • Patch: increment for backward-compatible corrections and clarifications that do not change a contract.
<meta name="design-system-version" content="0.1.1">

<footer class="ds-footer">
  <p><span class="ds-version">Design system v0.1.1</span> · ...</p>
</footer>

Compatibility requirement: record an exact version, not “latest” or a range. Review the document before changing its declared version. The audited source commit identifies evidence provenance and is not a substitute for the design-system version.
