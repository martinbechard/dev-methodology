Agent And Skill Specialization Examples

These examples show how PROJECT.yaml can keep root guidance, nested guidance, folder technology skillsets, and workflow-specific conceptual roles explicit for different repository structures.

This page uses three customer-safe configurations to demonstrate project-structure specialization: a root-only tool, a multi-tier application with nested guidance, and a wiki repository with separate source and synthesis workflows.

Configuration Examples By Project Structure

Each example is a focused PROJECT.yaml excerpt. The snippets omit full source-evidence, confirmation, and validation fields. The linked template defines the complete project configuration shape. The create-project-configuration skill owns project setup validation, and render-agents-technology-skills.py renders AGENTS.md guidance from accepted configuration data.

Northwind Tools: Root-Only Guidance

This example demonstrates root-only guidance. A single TypeScript runtime and common test workflow do not justify nested AGENTS.md files. Technology skills remain scoped to source and tests.

schema: project
schema_version: 1
project_setup:
  mode: basic
  concurrent_tasking: false
  persistence: none
  commit: main-branch
  documentation: wiki
  core_skill_delivery:
    mode: by-reference
    source: installed-agent-metadata
  technology_skill_delivery: by-reference
project_taxonomy:
  family: local-developer-tooling
  primary_runtime: Node.js
  application_tiers:
    - name: CLI and file processing
      paths: [src/**]
      stacks: [TypeScript]
root_agents_reference:
  file: AGENTS.md
nested_agents_files: []
technology_skill_loadouts:
  - scope: source
    pathPattern: src/**
    skills: [node-cli, typescript, typescript-esm, typescript-strict]
  - scope: tests
    pathPattern: tests/**
    skills: [node-cli, typescript, typescript-esm, typescript-strict, vitest]
workflow_selection:
  persistence:
    default: none
  commit:
    default: main-branch
validation_plan:
  commands:
    - command: pnpm test
      proves: command and fixture behavior
    - command: pnpm run build
      proves: package compilation

Acme Ledger: Nested Tier Guidance

This example demonstrates tier-specific specialization. The front-end tier gives taxonomy context. API contracts and database migration rules require nested guidance and specialized skill loadouts.

schema: project
schema_version: 1
project_taxonomy:
  family: web-application
  application_tiers:
    - name: Front-end
      paths: [app/(authenticated)/**, components/**]
      stacks: [Next.js, React]
    - name: API
      paths: [app/api/**]
      stacks: [Next.js routes]
    - name: DB
      paths: [db/**, drizzle/**]
      stacks: [Postgres, Drizzle]
root_agents_reference:
  file: AGENTS.md
nested_agents_files:
  - path: app/api/AGENTS.md
    needed: true
    reason: shared authentication and request-contract checks
  - path: db/AGENTS.md
    needed: true
    reason: migration, rollback, and sensitive-data rules
  - path: drizzle/AGENTS.md
    needed: true
    reason: migration generation and schema-change review rules
technology_skill_loadouts:
  - scope: API
    pathPattern: app/api/**
    skills: [api-routes, clerk-auth, postgres-drizzle, sql]
  - scope: DB
    pathPattern: db/**
    skills: [postgres-drizzle, sql, typescript, typescript-strict, jest]
  - scope: Drizzle schema
    pathPattern: drizzle/**
    skills: [postgres-drizzle, sql, typescript, typescript-strict, jest]

Beacon Knowledge Base: Workflow Separation

This example demonstrates workflow specialization within one root guidance file. Role ownership keeps human source notes, unprocessed raw sources, processed sources, and durable wiki synthesis separate.

schema: project
schema_version: 1
project_taxonomy:
  family: documentation-and-project-wiki
  application_tiers:
    - name: Human source notes
      paths: [Clippings/**]
      stacks: [Human-saved source notes]
    - name: Raw source folder
      paths: [raw/**]
      stacks: [Raw source artifacts]
      notes: raw/** is the whole raw-source tree; unprocessed sources remain outside raw/processed/**
    - name: Completed source boundary
      paths: [raw/processed/**]
      stacks: [Processed source artifacts]
      notes: raw/processed/** contains fully processed sources that passed the required ingest gates
    - name: Wiki synthesis
      paths: [docs/wiki/**]
      stacks: [Markdown project wiki]
root_agents_reference:
  file: AGENTS.md
nested_agents_files: []
role_agent_set:
  - role: wiki-source-collector
    purpose: collect public raw source artifacts and leave docs/wiki unchanged
    owns:
      - raw source artifacts with source URLs, visible dates, and exclusions
    hands_off:
      - raw evidence inventory to wiki-ingester for durable synthesis
    skills: [project-wiki-research, project-wiki]
    completion_checks:
      - raw evidence, exclusions, and collection window recorded
      - docs/wiki unchanged
  - role: wiki-ingester
    purpose: process approved raw inputs into durable wiki coverage
    owns:
      - docs/wiki edits, raw/processed moves, source-link corrections, and ingest state
    hands_off:
      - topic-page verification to wiki-topic-verifier with read-only authority
    skills: [project-wiki, project-wiki-topic-write]
    conditional_skills:
      - skill: code-project-wiki
        condition: when durable wiki claims depend on implementation behavior that must remain traceable to authoritative code and tests.
      - skill: terminology-standard
        condition: when ingest creates or revises durable wiki prose governed by a project or shared user Terminology Standard.
    completion_checks:
      - leaf linking, lint, OKF validation, and GOOD pre-move verifier verdict
      - source moved to raw/processed only after GOOD pre-move verdict
      - processed-source links validated with any required post-move verifier gate
  - role: wiki-writer
    purpose: maintain durable wiki topic pages outside raw-source ingest
    owns:
      - docs/wiki topic pages, hubs, links, digests, and code-aware knowledge
    hands_off:
      - changed-page review to wiki-topic-verifier with read-only authority
    skills: [project-wiki, project-wiki-topic-write]
    conditional_skills:
      - skill: code-project-wiki
        condition: when wiki maintenance depends on code, tests, procedures, backlog state, or commit-range evidence.
      - skill: terminology-standard
        condition: when creating or revising durable wiki prose governed by a project or shared user Terminology Standard.
    completion_checks:
      - leaf linking, lint, applicable OKF validation, and GOOD verifier verdict
  - role: wiki-topic-verifier
    purpose: independently verify supplied wiki topic pages in a fresh read-only context
    owns:
      - verification verdicts for page contract, durable leaf coverage, source links, digests, federation, lint, and OKF status
    hands_off:
      - actionable file-specific corrections to the assigning wiki-ingester or wiki-writer
    skills: [project-wiki-topic-verify]
    conditional_skills:
      - skill: terminology-standard-review
        condition: when the verified topic pages are governed by a project or shared user Terminology Standard.
    completion_checks:
      - return GOOD or NEEDS_CORRECTION without editing files
      - include the reviewed page inventory and evidence sources
validation_plan:
  commands:
    - command: python3 "$PROJECT_WIKI_SKILL_ROOT/scripts/wiki_ops.py" status
      proves: wiki root, raw queue, and source state are inspectable
    - command: python3 "$PROJECT_WIKI_SKILL_ROOT/scripts/wiki_ops.py" link-leaves
      proves: durable leaf references are linked
    - command: python3 "$PROJECT_WIKI_SKILL_ROOT/scripts/wiki_ops.py" lint
      proves: wiki structure and source links are valid
    - command: python3 "$PROJECT_WIKI_SKILL_ROOT/scripts/wiki_ops.py" okf-validate
      proves: OKF topic metadata is valid
