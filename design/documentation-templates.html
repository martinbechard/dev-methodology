Documentation Templates

The development methodology ships eight source-backed templates: one PROJECT.yaml configuration template, six methodology document templates, and one file-backed Work item template. The methodology document templates cover project wiki, functional specification, architecture, high-level design, module design, and unit test plan artifacts. Each template supplies TODO instructions that are replaced with project evidence when an artifact is created.

Records the repository's setup choices for Agent and Skill operation, including delivery mode, coordination, Persistence and Commit selectors, documentation mode, shared and project skill routing, folder rules, guidance files, and validation evidence.

Architecture

Defines project-wide boundaries, system context, technology stack, file ownership, dependency layers, major components, cross-cutting concerns, invariants, risks, and verification. Its taxonomy identity remains distinct from HLD, and its authority flows to child HLDs and component designs without circular references.

  • Scope: a system or cross-cutting architectural concern
  • Default identity: docs/architecture/ARC-NNN-slug.md
  • Structured workflow outputs such as architecture-design.yaml retain separate ownership and lifecycle
  • Creator: create-architecture
  • Reviewer: review-architecture
architecture-template.md

File-Backed Work Item

Records one file-provider Work item or series child with canonical metadata, source evidence, requirements, acceptance criteria, dependencies, verification, technical questions, lifecycle state, and any genuine user-action boundary.

  • Scope: one file-backed Work item; Ready is dispatchable, Blocked waits on a hard dependency, Holding is explicit deferral, and User Action Required waits on one user-owned answer.
  • Creator: create-work-item-file
  • Final check: create-work-item-file Final Check And Result

Template Workflow

Choose the artifact that owns the requested knowledge, apply its structural and prose authorities, then complete and maintain it from project evidence.

Template Selection

Choose the smallest artifact that fully owns the requested knowledge. Project configuration and wiki methodology establish operating context. Functional specification, architecture, high-level design, module design, and unit test plan templates form a progressively narrower development chain. The file-backed Work item template stores cross-cutting Work-item content, not a prerequisite or successor in that chain.

Question to answer Template Relationship to other artifacts
Which agents, skills, folder rules, and guidance files apply to this repository? Project Configuration Establishes setup intent for later agent work; it is not a product or implementation design.
How should durable project knowledge be organized, sourced, maintained, and verified? Project Wiki Methodology Defines the synthesis layer that links the authoritative specifications, designs, source, tests, and backlog.
What must a user, operator, administrator, service, or external system be able to accomplish? Functional Specification Supplies accepted behavior and workflows to architecture and downstream design.
What system-wide structure, boundaries, stack, and dependency rules govern implementation? Architecture Constrains child high-level designs while leaving detailed operation contracts, leaf assignments, and implementation sequencing to them; its taxonomy identity and authority remain distinct.
How do several components collaborate to deliver a subsystem or feature family? High-Level Design Accounts for accepted requirements and divides them into implementable module responsibilities.
What exact contract, state, processing, dependencies, and error behavior belong to one unit? Module Design Provides the implementation-ready boundary consumed by coding and test work.
Which scenarios prove one unit's behavior, boundaries, failures, and invariants? Unit Test Plan Translates accepted contracts and implementation evidence into durable test obligations.
What source-backed Work item should enter the file-provider queue, and does a genuine user-owned answer block it? File-Backed Work Item Records a cross-cutting provider item. Ready is dispatchable; Blocked has an unmet hard dependency; Holding is explicitly deferred; User Action Required has one user-owned answer.

Artifact Authoring Boundaries

A selected template controls the artifact structure and required sections. The ste-technical-writing skill controls technical prose inside that structure.

Template structure authority

  • Keep the selected artifact's required sections, order, and optional-section rules from the owning creation skill.
  • Keep descriptions, requirements, decisions, and procedures in their source-defined forms.
  • Use structured-explanation only for a technical reasoning section that needs its item model.

Technical prose authority

  • Preserve exact identifiers, values, conditions, ownership, quotations, and normative force.
  • Apply clear technical prose to headings, lists, tables, captions, and structured-explanation synopses.
  • Do not rewrite code, commands, schemas, machine-readable data, fixed labels, or quotations.
  • Do not claim formal ASD-STE100 verification or certification.

Template Completion

Source-backed artifact completion

  • Copy only the template that matches the requested artifact.
  • Replace every TODO instruction with project-specific evidence.
  • Link authoritative sources, code, tests, backlog records, and related pages where the explanation depends on them.
  • Use Not yet identified when a required source, implementation, test, or related record does not exist.

Artifact review

  • Run the matching reviewer or verifier after the artifact is complete.
  • Use create-work-item-file Final Check And Result for file-backed Work items.
  • Keep steady-state prose and record unresolved decisions explicitly.
  • Add editable Mermaid diagrams when real sequence, handoff, branch, lifecycle, data, or structural relationships trigger them.

Ongoing maintenance

Recheck the document when its sources, responsibilities, contracts, or verification evidence change.

Wiki Format

The Project Wiki Methodology template can define a project wiki under docs/wiki as compiled understanding rather than primary authority. This page includes the repository and topic-page formats that README.md assigns to it. The project-wiki page schema owns the concrete format for topic pages, folders, and required root files.

Wiki repository shape

  • README.md introduces the wiki and its primary navigation.
  • schema.md records authority, page sections, and maintenance rules.
  • topic-index.md maps topics and their source neighborhoods.
  • glossary.md defines recurring project terminology.
  • open-decisions.md records unresolved source conflicts and decisions.
  • known-defects.md explains how to interpret defect records.
  • maintenance-log.md records notable maintenance events.
  • Topic folders use index.md hub pages plus granular leaf pages.
  • digests/index.md and YYYY-MM.md pages summarize ingested developments when digests apply.

Shared contract scope

The code example shows the eight shared sections for docs/wiki topic pages. The same shared sections start the six methodology document templates. PROJECT.yaml and file-backed Work items keep their own formats.

Topic page organization

  • Non-reserved concept pages use YAML frontmatter with a non-empty type; title, description, and tags improve routing and previews.
  • Folder index.md and log.md files are reserved navigation pages and do not need concept frontmatter.
  • Hub pages describe a stable domain and link to granular leaves that can change or be maintained independently.
  • Additional topic-specific sections may follow the shared contract without replacing its required sections.
  • The six methodology document templates keep the eight shared sections first and append the extension sections owned by their template.

Format boundary: the shared wiki-compatible contract applies to docs/wiki topic pages and the six methodology document templates. It does not apply to PROJECT.yaml, file-backed Work items, README files, design HTML pages, runtime schemas, generated data, or native agent definitions that already have another authoritative format.

Read the complete project wiki page schema for leaf splitting, digest ordering, source-link, OKF, and maintenance rules. The Wiki Skills And Project Context page explains how that page format participates in persistent synthesis, source authority, independent verification, and code-aware synchronization.
