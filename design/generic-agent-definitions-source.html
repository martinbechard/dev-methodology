Generic Agent Definitions Source

Conceptual roles under agents/roles/ own agent intent, agents/role-schema.yaml owns the allowed vocabulary, and the model-profile sources own semantic profile IDs and concrete runtime model values. The default generator owns the transformation that preserves fixed and conditional core-skill semantics while emitting native by-reference bindings. Explicit inline remains available for self-contained runtimes. The generator also produces the generation manifest from those source values, recording the chosen mode and agent digests so installation metadata can prove that the installed bytes use the same delivery contract.

Skills and agents have different portability models. A source skill remains the same portable skill package when it is deployed, while a conceptual agent definition source must be converted into the file format and properties understood by each agent harness. This page explains that difference, then separates canonical inputs and constraints from generated outputs before covering conceptual semantics, model resolution, native packaging, cross-runtime adapter mappings, and vendor references.

The Portability Problem

A repository that supports several agent harnesses must distinguish portable skill packages from harness-specific native agent definitions. Treating both as though they had the same source and runtime format creates duplicate agent files, ambiguous ownership, and drift.

Skills Have A Portable File Standard

The source skill definition is also the runtime skill definition. skills/<skill-name>/SKILL.md is copied into the selected skill directory without translating its frontmatter or instruction body into another format.

  • The portable SKILL.md remains authoritative before and after deployment.
  • Supporting files in the skill directory remain part of the same portable package.
  • Adjacent harness metadata, such as Codex agents/openai.yaml, supplements the package for that harness; it does not replace or rewrite SKILL.md.
  • A harness-specific skill source under adapters/<harness-name>/skills/ uses the same package format but is installed only with that adapter.

Agents Do Not Have One Portable Runtime File

Agent harnesses discover different files, use different serialization formats, and expose different property names and capabilities. The same conceptual agent definition might otherwise need separate hand-maintained TOML, Markdown, YAML frontmatter, and harness-specific configuration.

  • Discovery directories and filename extensions differ by harness.
  • Equivalent behavior may be a native property in one harness and instruction text in another.
  • Model, tool, permission, isolation, memory, and skill fields are not uniformly named or supported.

From Conceptual Agent Definitions To Native Agent Definitions

agents/roles/<role-category>/<role-name>.role.yaml is a conceptual agent definition source, not a file that an agent harness loads directly. It owns the agent's conceptual values, including its selected profile ID, in the repository's shared vocabulary. agents/role-schema.yaml constrains those values, the conceptual profile catalog owns profile purposes, and adapter model-profile YAML owns concrete model and any effort or context values present. scripts/build-skill-docs.py owns the transformation that emits one native agent definition per supported harness.

1. Author The Conceptual Agent Definition

Define intent with conceptual properties such as instructions, skills, modelProfile, tools, and outputContract. These properties describe the agent without making a harness file authoritative.

2. Validate And Resolve

agents/role-schema.yaml defines the allowed conceptual agent definition properties. Skill IDs resolve against portable skill sources, semantic model profiles resolve through adapter model mappings, adapter-owned skills resolve only within their harness, and unsupported or defaulted behavior follows the documented adapter rules.

3. Render Each Harness Format

scripts/build-skill-docs.py owns conversion to native property names, Codex runtime-name normalization and output-filename derivation, instruction placement, explicit omissions, skill-reference and inline-skill handling, and runtime file structures. For example, conceptual instructions becomes Codex developer_instructions or the Markdown body of a Claude Code, Gemini CLI, or Junie CLI agent. Conceptual roles and skills still own their source values, and adapter model-profile YAML owns only the concrete model and any effort or context values present for its harness.

The Codex adapter includes codex-harness-directives in that required core set when repositoryMutation is required or conditional. Passing --inline-core-skills true explicitly embeds required core skill bodies. The cross-harness skill lifecycle owns the preload, dynamic invocation, content-read, application, and proof distinctions.

4. Use Generated Native Agent Definition Files

The generated Codex TOML and Claude Code, Gemini CLI, and Junie CLI Markdown files are deployable runtime artifacts. Their conceptual values come from roles, schema-governed defaults, referenced skills, and model-profile sources; scripts/build-skill-docs.py owns their native transformation and file structure. The generated files must not become independent sources of truth.

Property conversion is not just a filename change

  • Rename or relocate: a conceptual property may become a differently named native property or move into an instruction body.
  • Resolve: a provider-neutral value such as modelProfile: advanced becomes the concrete model and reasoning settings selected by an adapter.
  • Expand: source-owned skill conditions, output contracts, and rationale can become generator-rendered native fields, instructions, or trace comments.
  • Default or omit: behavior without a native equivalent follows an explicit fallback rule instead of inventing an unsupported harness property.

Conceptual Agent Definition Properties

These are conceptual source-model properties, not a claim that every harness has a native field with the same name. The conceptual set captures the intent needed to define a reusable agent once. The later mapping table shows how each property becomes native metadata, instruction text, comments, a resolved value, or an explicit omission.

Element Conceptual Definition Property Meaning In The Source Definition
Name name Names the agent type used by routing, references, generated files, and UI display. The conceptual role owns the portable name and filename values; scripts/build-skill-docs.py owns runtime normalization and derived output filenames. Use a stable, short name that can survive adapter generation.
Filename filename Controls discovery and precedence in runtimes that load agent files from scoped folders. Keep it aligned with the name unless the runtime explicitly allows a different display name.
Description description Explains the agent's purpose and when a parent agent or user should delegate to it. This is a routing field, so it should be concise and specific.
Instructions instructions Defines behavior, boundaries, workflow, deliverables, and handoff expectations. Concise single-phase conceptual agent definitions may use a string. Definitions with branches, delegation, review loops, failure handling, or several terminal criteria use the validated structured mapping; generators render its sections into one portable runtime instruction string.
Skills skills Stores ordered skill entries with a skill identifier, justification, and optional condition. The skills modularization page explains when each entry applies.
Agent dependencies agentDependencies Names fixed direct agent-to-agent use declared by this conceptual definition. The conceptual role owns each dependency relationship, and the generated diagram renders its arrow from the using agent to each used agent; runtime-selected delegation that is not a fixed dependency remains outside this list.
Skill condition skills[].condition Stores the optional human-readable condition beneath one skill entry; generators serialize it into runtime instructions.
Skill availability skillAvailability Stores explicit name-based or path-based availability overrides for adapters that expose them.
Tools tools Lists tools or tool groups the agent may use. Some runtimes treat this as an allowlist; some default to all tools when omitted.
Disallowed tools disallowedTools Lists tools or tool groups the agent must not use. Keep this separate from tools because allowlists and denylists resolve differently across runtimes.
MCP servers mcpServers Names adapter-specific server allowlists when a conceptual role must narrow session access. Connection commands, environment boundaries, and credentials remain host deployment configuration.
Model profile modelProfile Selects simple, default, documentation, advanced, or advanced-long capability without naming a provider model. Adapter mappings resolve the native model and reasoning settings.
Stage model profiles modelStages Declares intended semantic profiles for bounded stages. Separate stage invocations must be implemented and captured before staged execution is considered verified.
Dynamic folder skills dynamicFolderSkills Records that the agent consumes folder skills supplied through project guidance; selection remains outside the conceptual definition source.
Repository mutation repositoryMutation Declares whether repository mutation is required, conditional, or never allowed for the agent. This capability is independent from project resource coordination, and generation rejects a conceptual role that directly loads the selected agent-claim implementation. Generation also rejects read-only isolation for required or conditional mutation. The Codex adapter separately uses required or conditional mutation to load its harness directives skill.
Max turns maxTurns Caps the number of agentic turns or steps before the agent must return.
Timeout timeout Caps agent-level elapsed execution time. An adapter must not substitute an unrelated MCP startup timeout.
Permission mode permissionMode Controls when actions run automatically, ask for approval, or are blocked. This is not the same as tools because a visible tool or command may still require an approval decision.
Isolation isolation Controls filesystem, network, or workspace isolation where supported. Keep it separate from permission mode because sandboxing changes what the agent can reach, not only what it may ask to do. Read-only isolation is valid only when repository mutation is never allowed. Conditional reviewers retain a writable sandbox so they can claim and save scoped review evidence. They remain prohibited from modifying the artifact under review.
Memory memory Controls persistent memory scope or names the guidance sources the agent should read before working.
Output contract outputContract Describes what the agent returns, what evidence it includes, and how another agent or human should continue from its result.
Examples examples Stores customer-safe runtime invocations and plausible responses that remain owned by the conceptual role when rendered in generated catalog views and regression checks. Adapter-specific invocations use that harness's native selector, including underscore-normalized Codex agent names.

Semantic Model Profiles And Adapter Resolution

Model selection has two source layers. The conceptual catalog owns provider-neutral profile IDs and purposes; each adapter model-profile mapping owns the concrete model and any effort or context values present for the same IDs. scripts/build-skill-docs.py loads and validates those fields, renders model for Codex, Claude Code, Gemini CLI, and Junie CLI, renders effort only for Codex and Junie CLI, and currently renders no context field.

Conceptual capability catalog

agents/model-profiles.yaml owns the profile IDs and their purposes. Conceptual roles select one of those IDs through modelProfile or assign bounded stage IDs through modelStages.

Harness adapter mappings

adapters/<harness-name>/model-profiles.yaml owns the accepted concrete model, optional effort, and optional context values for its harness. scripts/build-skill-docs.py requires each adapter to map the complete conceptual profile set, then owns which accepted values are rendered and their native property names: all four adapters receive model, Codex and Junie CLI also receive effort, and no adapter currently receives context.
