A practical operating model for many agents and one codebase

Orchestrated Development Lifecycle

Work moves through one visible queue, one private delivery lane per item, and short coordination gates only when agents must touch the same shared object. The process keeps decisions, implementation, review, integration, and completion understandable without tying the method to one agent runtime.

Methodology installation first chooses and records core-skill delivery while generating and installing matching native agents. Later project setup reuses that evidence, creates PROJECT.yaml and only the selected empty wiki or specification roots, and never runs reverse engineering. Explicit later documentation and development workflows consume the accepted configuration and routed skill references.

Work-Item Continuity

The work item's status, decisions, owner, accepted change, verification, and delivery evidence travel together from intake to completion.

Chapter 01

Work-Item Backlog

The backlog separates what the work is from where it happens. A work item is classified by outcome, then moved through a small set of explicit states.

Work-Item Types

Feature
Add or expand a capability.
Defect
Correct broken or regressed behavior.
Analysis
Produce an evidence-backed answer or recommendation.
Investigation
Trace an unclear failure or risk until the next action is known.

Work-Item Readiness

Clear outcome
Requirements and acceptance criteria are observable.
Known authority
Approvals and user-owned decisions are recorded.
Dependencies
Required predecessors are complete or explicitly absent.
Verification
The item says how completion will be demonstrated.
Chapter 02

File-Backed Work Items

A file provider stores each work item as Markdown in the repository. The file is readable in review, versioned with the project, and sufficient for a future agent to continue without the original conversation.

The Work item is the only durable provider record. File-provider creation and lifecycle procedures are defined by Create File Work Item and Manage File Work Items.

New Work-Item Notification

After a new work item is persisted, its creator sends the opaque provider-owned Work Item ID to the existing Coordinator task. The message prompts a fresh inventory read. It does not reserve capacity, change lifecycle state, create a delivery task, or start implementation. If no Coordinator task is available, the committed item remains in provider inventory for the next read.

Chapter 03

Agent Roles

A Role is a reusable responsibility and authority contract applied to a runtime Agent; each Agent below owns one distinct kind of decision.

Execution Contexts

The Dev Backlog Watchdog is a standing read-only child Agent outside delivery capacity. The Dev Backlog Steward is a child Agent, not another work-item Thread or queue entry. It performs only explicitly delegated provider mutations.

An Assignment is bounded work sent to an Agent; it does not create another work-item Thread. A runtime may retain a child execution context for that Agent, but the methodology still treats it as part of the owning parent or work-item Thread.

The development-agent catalog owns the complete Role definitions. Work-item coordination owns the execution-context model.

Chapter 04

Runtime Coordination

Runtime Coordination Surfaces

The shared coordinate-codex-work-items skill is the single normative authority for active-execution eligibility, capacity, runtime reconciliation, and conversation-title synchronization in an explicitly requested multi-item Codex campaign. Dev Backlog Coordinator, Dev Backlog Steward, Dev Orchestrator, and Dev Backlog Watchdog select that skill for their applicable responsibilities. The file-provider manager remains atomic and does not own runtime state.

Dev Backlog Steward synchronizes the conversation title after every successful lifecycle transition. It renames directly when the runtime permits it; otherwise it sends the exact title to the canonical conversation owner or runtime coordinator and verifies that handoff. The conversation keeps a stable identity. Its title remains display state and never replaces provider, active-execution, Git, review, verification, or coordination-registry evidence.

Backlog Blockage Recovery And Dispatch Mode

The user or Watchdog may declare a backlog blockage when the documented conditions apply. Resolve Backlog Blockage owns diagnosis and one-item-at-a-time recovery without claims or delegated delivery.

When a secondary-thread dispatch mechanism exists, Set Solo Mode disables only new secondary-thread dispatch at recovery entry. Set Multitask Mode enables new dispatch only after every blockage item is terminal, no Blocked item remains, all recovery changes are committed, and required verification has a concrete disposition.

Repeated transitions preserve the effective setting. Recovery proceeds without either mode skill when no secondary-thread dispatch mechanism exists.

Private Workspaces

Starting and Running Work items use separate worktrees. Their files, outputs, and caches remain separate until delivery.

Chapter 06

Shared-Resource Coordination

PROJECT.yaml may load Agent Claim when the project needs temporary protection for shared files or resources. The claim registry records temporary ownership; it does not prove review, delivery, or completion.

Claim Cleanup

Release removes the named live claim while the registry is locked and records a RELEASED event. It does not inspect Git state or decide whether delivery completed. After a Coordinator restart with all prior agents stopped, reset creates an empty claim registry before new work is dispatched.

Claim Limits

A claim records temporary ownership. Request the smallest known exact path or resource manifest; do not request the whole project for a fixed subset. Review, verification, Git delivery, and work-item completion require separate evidence.

Agent Claim is the only source for claim events, scopes, conflicts, deadlines, recovery, and release timing. The command helper and MCP helper describe only how to invoke the configured helper.

Chapter 07

Delivery Stages

Production work is accepted in layers. Review asks whether the change is correct and maintainable; verification proves the required behavior; delivery integrates the accepted result through the configured path.

Direct-main delivery

  1. Review and verify the private candidate.
  2. Follow Agent Claim when it is loaded.
  3. Refresh current main and create a fresh reconciliation branch from that exact commit.
  4. Apply only the accepted paths; do not import unrelated ancestry merely to preserve history. Verify the integrated result, update main, and complete delivery closeout.

Feature-branch delivery

  1. Review and verify the feature branch.
  2. The Commit skill publishes a GitHub pull request or GitLab merge request and returns Commit AWAITING_REVIEW without Persistence mutation.
  3. Dev Orchestrator separately dispatches Dev Backlog Steward exactly once for the nonterminal AWAITING_REVIEW update; repeated observation reconciles that update.
  4. Resume the same delivery identity through provider-accurate review, checks, merge, and main observation until Commit READY, then dispatch exactly once for the distinct terminal Persistence closure. Provider none keeps both states thread-local.
Integration Cleanup

Create a fresh reconciliation branch from current main for integration; this becomes the work-item Thread's integration and cleanup branch. An older candidate branch retained only as a non-ancestral content source is handled separately.

Before handoff, commit completed work and prove the applicable worktree clean.

Direct-main and pull-request details are defined by Direct-Main Completion, Feature-Branch Completion, and Create Pull Request.

Chapter 08

Blocker Recovery

Known Blocker Handoff

Orchestrator Blocker Steps

  1. Stop unsafe work.
  2. Preserve commits and evidence.
  3. Resolve resource ownership truthfully.
  4. Notify the Coordinator immediately.

Blocker Notification Fields

Cause
Exact blocker and owner.
Exit
Observable unblock condition and requested action.
Identity
Canonical Thread and root Agent identity.
Resume
Whether resumption is safe.

Coordinator Sequence

  1. Acknowledge and reconcile the complete handoff.
  2. After exhausted corrections, return exactly one immutable decision: a recovery with evidence linked to every finding, one similarly linked bounded retry, one explained genuine user decision with options and tradeoffs, or one continuing external or technical dependency with an observable trigger.
  3. Reject indefinite Blocked and delegate only the resulting provider mutation to the Steward. Consume a bounded retry before reconciling again, and do not repeat it.
Execution Safeguards

Findings return to the original producer. After two failed correction attempts for the same criterion, preserve the canonical task, candidate, review, verification, Git, claim, and attempt history before returning exactly one concrete disposition decision for Steward application. A fresh retry is bounded to one attempt, links its evidence to every unresolved finding, and is consumed before another reconciliation.

Before a phase expected to exceed five minutes, publish the active unit, estimate, hard stop, retained evidence path, and distinct acceptance criterion. After an expensive failure, classify retained evidence, add the smallest offline regression, and run one cheapest representative first.

Chapter 09

User Decision Gates

Agents resolve technical questions from evidence. A work item moves to User Action Required only when the next safe step depends on authority, intent, risk acceptance, or information that belongs to the user.

Coordinator inability alone does not manufacture a user obligation. A technical or external cause remains Blocked with an exact owner and observable unblock condition until one concrete action genuinely belongs to the user.

1 · Recorded State

The Coordinator selects User Action Required and the provider records it before the request is presented.

2 · Clear Question

Ask one plain-language question and explain why the user owns the answer.

3 · Consequences And Boundary

Give evidence-backed options or an illustrative example. State each consequence and exactly what unattended work stops.

4 · Decision Record

Store the exact answer, date, provenance, approved scope, and exclusions.

5 · Same-Thread Resume

The Coordinator decides routing. With a provider, Stewards record Ready, Starting, and Running; provider none keeps equivalent evidence thread-locally.

The same root Orchestrator resumes the existing Thread; no replacement is created. The user does not need to repeat the answer in the parent Thread. A user answer resolves the decision gate, not delivery. Work produced before reconciliation is preserved for ownership, scope, review, verification, and delivery checks. Thread location alone never invalidates it.

Chapter 11

Design And Documentation Workflows

Design and documentation change the producer and reviewer, not the lifecycle. They still start from an authorized work item, proceed in a private lane, receive independent review, pass focused verification, and use the configured delivery path.

Functional intent

Actors, outcomes, permissions, workflows, and constraints.

Architecture

System boundaries, trust, dependencies, and cross-cutting decisions.

High-level design

Feature families, modules, interactions, and implementation order.

Module design

Implementable contracts, states, failure behavior, and verification obligations.

Implementation

Code and tests preserve the accepted design through review and verification.

Planned Development

Accepted functional specifications and architecture are upstream authority. Create and review high-level and module designs before dependent implementation. Documentation acceptance and implementation readiness are separate decisions: an accurate document may be accepted while an unresolved high-impact contract blocks downstream work.

Whole-Project Reverse Engineering

The persisted hybrid-specifications-and-wiki mode keeps structured specifications authoritative. Work proceeds bottom-up from source and module evidence, then performs a final top-down semantic reconciliation through wiki, functional specifications, architecture, high-level designs, module designs, and source.
