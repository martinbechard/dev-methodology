A practical operating model for many agents and one codebase

Orchestrated Development Lifecycle

Work moves through one visible queue, one private delivery lane per item, and short coordination gates only when agents must touch the same shared object. The process keeps decisions, implementation, review, integration, and completion understandable without tying the method to one agent runtime.

Methodology installation first chooses and records core-skill delivery while generating and installing matching native agents. Later project setup reuses that evidence, creates PROJECT.yaml and only the selected empty wiki or specification roots, and never runs reverse engineering. Explicit later documentation and development workflows consume the accepted configuration and routed skill references.

Work-Item Continuity

The work item's status, decisions, owner, accepted change, verification, and delivery evidence travel together from intake to completion.

Chapter 01

Work-Item Backlog

The backlog separates what the work is from where it happens. A work item is classified by outcome, then moved through a small set of explicit states.

Work-Item Types

Feature
Add or expand a capability.
Defect
Correct broken or regressed behavior.
Analysis
Produce an evidence-backed answer or recommendation.
Investigation
Trace an unclear failure or risk until the next action is known.

Work-Item Readiness

Clear outcome
Requirements and acceptance criteria are observable.
Known authority
Approvals and user-owned decisions are recorded.
Dependencies
Required predecessors are complete or explicitly absent.
Verification
The item says how completion will be demonstrated.

Chapter 03

Agent Roles

A Role is a reusable responsibility and authority contract applied to a runtime Agent; each Agent below owns one distinct kind of decision.

Execution Contexts

The Dev Backlog Steward is a child Agent, not another work-item Thread or queue entry. An Assignment is bounded work sent to an Agent; it does not create another work-item Thread. A runtime may retain a child execution context for that Agent, but the methodology still treats it as part of the owning parent or work-item Thread.

The development-agent catalog owns the complete Role definitions. Work-item coordination owns the execution-context model.

Chapter 04

Private Workspaces And Delivery Paths

Starting and Running Work items do not share a mutable checkout. Each work-item Thread uses its own branch and worktree, so ordinary implementation, corrections, local tests, and read-only review can proceed independently.

Direct-main delivery

  1. Review and verify the private candidate.
  2. When resource coordination is enabled, acquire the exact shared integration paths and integration resource; with none, enter the serialized integration transaction without claim operations or evidence.
  3. Refresh current main and create a fresh reconciliation branch from that exact commit.
  4. Apply only the accepted paths; do not import unrelated ancestry merely for provenance. Verify the integrated result, update main, and complete delivery closeout with coordination evidence only when enabled.

Feature-branch delivery

  1. Review and verify the feature branch.
  2. The Commit skill publishes a GitHub pull request or GitLab merge request and returns Commit AWAITING_REVIEW without Persistence mutation.
  3. Dev Orchestrator separately dispatches Dev Backlog Steward exactly once for the nonterminal AWAITING_REVIEW update; repeated observation reconciles that update.
  4. Resume the same delivery identity through provider-accurate review, checks, merge, and main observation until Commit READY, then dispatch exactly once for the distinct terminal Persistence closure. Provider none keeps both states thread-local.
Chapter 05

Shared-Resource Coordination

PROJECT.yaml selects resource coordination independently as none or agent-claim. Private work is parallel by default. When agent-claim is selected, a deadline-bound coordination claim protects shared objects and its registry remains a temporary conflict-avoidance scratchpad rather than delivery authority. When none is selected, the lifecycle records no claim procedure or evidence and relies on explicit assignment scope plus serialized delivery transactions.

Claim Outcomes

Acquired
The named writer may use the recorded shared scope.
Wait required
Another live writer overlaps; coordinate release or narrow the requested scope.
Isolation required
Non-overlapping work needs its own branch and worktree.
Recovery authority required
Dirty unclaimed state must be preserved before another writer proceeds.

Claim Limits

Quality
It is not proof of review, verification, delivery, or work-item completion.
Commit scope
It does not audit commit history or decide whether committed paths belong to the contribution. Normal release does not inspect history; reconciliation checks only bounded commit existence, ancestry, exact paths, claimed-domain exclusion, and current-tree match.
Integration
Independent review and integration own committed-content, changed-path, and provenance decisions.
Lifecycle
Registry cleanup, Git integration, and backlog closeout are distinct operations.
Resource Deadlines

Each named resource records its exact class and id, expected duration (the planned working time), requested hard stop (the owner-requested latest finish), configured maximum (the immutable project-policy cap), expected release (acquisition time plus expected duration), absolute hard stop (acquisition time plus the accepted requested duration), and cleanup grace (the bounded post-stop shutdown window). The initial maximum/grace defaults in seconds are backlog mutation 600/120, main integration 2700/600, browser or server 3600/600, database or port 1800/300, and live or model evaluation 14400/1800. Exact-id overrides are explicit project policy.

Heartbeat reports liveness and never extends the hard stop. An evidence-backed extension stays within the immutable maximum. Status is read-only, overdue state never auto-releases ownership, and a stopped owner is immediately actionable. Cleanup grace is for shutdown and evidence preservation, not continued work.

Release Reconciliation Recovery

The durable transaction marker binds the canonical registry target to exact original and released snapshots and the canonical journal target to exact original, prepared, and released snapshots. A prepared marker protects the original claim; its RELEASE_PENDING line is pending evidence only. A committed marker makes the released registry authoritative and finalizes exactly one RELEASED event. Recovery validates the complete marker, snapshot relationships, allowed target states, and every non-symbolic-link target component before writing.

Status and journal maintenance enter the registry recovery gate first. Maintenance acquires its journal lock only after marker recovery succeeds. Report remains read-only and returns RECONCILIATION_RECOVERY_REQUIRED before journal loading when a marker exists.

  1. Invoke status through the same configured transport.
  2. If recovery still cannot complete, preserve the marker, registry, journal, structured result, and filesystem evidence.
  3. Escalate the evidence without manually editing or removing transaction or claim state.
Shared-Resource Contention

Keep the existing Work item and delivery lane. Request direct release notification, retry only on the documented bounded schedule, and investigate the real owner and scope when the wait exceeds its limit. Never create a wait-only Work item, release protection for dirty unpreserved work, or treat a heartbeat as proof of useful progress.

The portable Agent Claim contract owns the exact outcomes, recovery, release, and administrative reset safeguards. Focused claim tests and operator guidance provide executable and operational detail.

Chapter 06

Delivery Stages

Production work is accepted in layers. Review asks whether the change is correct and maintainable; verification proves the required behavior; delivery integrates the accepted result through the configured path.

Execution Safeguards

Findings return to the original producer. After two failed correction attempts for the same criterion, a repeated failure signature, or an unavailable fixed dependency, preserve the candidate and record a truthful blocker.

Before a phase expected to exceed five minutes, publish the active unit, estimate, hard stop, retained evidence path, and distinct acceptance criterion. After an expensive failure, classify retained evidence, add the smallest offline regression, and run one cheapest representative first.

Direct-main and pull-request details are defined by Direct-Main Completion, Feature-Branch Completion, and Create Pull Request.

Chapter 07

User Decision Gates

Agents resolve technical questions from evidence. A work item moves to User Action Required only when the next safe step depends on authority, intent, risk acceptance, or information that belongs to the user.

1 · User Question

Record one concrete question, why it is needed, and the exact unattended boundary.

2 · Preserved Context

Keep the requirements, scope, options, and discovered evidence in the item.

3 · Decision Record

Store the exact answer, date, provenance, approved scope, and exclusions.

4 · Same-Thread Resume

The Coordinator decides routing. With a provider, Stewards record Ready, Starting, and Running; provider none keeps equivalent evidence thread-locally.

5 · Outcome Routing

Deferred work moves to Holding; a declined request receives its truthful disposition.

The same root Orchestrator resumes the existing Thread; no replacement is created. The user does not need to repeat the answer in the parent Thread. A user answer resolves the decision gate, not delivery. Work produced before reconciliation is preserved for ownership, scope, review, verification, and delivery checks; Thread location alone never invalidates it.

Administrative Cleanup

Reset only an inactive coordination entry whose work is preserved and whose resources are stopped or handed off. A reset changes temporary registry state only. It must not rewrite Git, edit project files, discard a worktree, manufacture a release event, or claim that delivery occurred.

Neither bundled coordination transport exposes reset, and manual registry editing is forbidden. If a host-supported targeted atomic reset is unavailable, stop and route the operation to an administrator.

Create a fresh reconciliation branch from current main for integration; this becomes the work-item Thread's integration and cleanup branch. An older candidate branch retained only as a non-ancestral content source is handled separately.

Chapter 09

Design And Documentation Workflows

Design and documentation change the producer and reviewer, not the lifecycle. They still start from an authorized work item, proceed in a private lane, receive independent review, pass focused verification, and use the configured delivery path.

Functional intent

Actors, outcomes, permissions, workflows, and constraints.

Architecture

System boundaries, trust, dependencies, and cross-cutting decisions.

High-level design

Feature families, modules, interactions, and implementation order.

Module design

Implementable contracts, states, failure behavior, and verification obligations.

Implementation

Code and tests preserve the accepted design through review and verification.

Planned Development

Accepted functional specifications and architecture are upstream authority. Create and review high-level and module designs before dependent implementation. Documentation acceptance and implementation readiness are separate decisions: an accurate document may be accepted while an unresolved high-impact contract blocks downstream work.

Whole-Project Reverse Engineering

The persisted hybrid-specifications-and-wiki mode keeps structured specifications authoritative. Work proceeds bottom-up from source and module evidence, then performs a final top-down semantic reconciliation through wiki, functional specifications, architecture, high-level designs, module designs, and source.
