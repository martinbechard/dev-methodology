Orchestrated Development Lifecycle

This page describes the steady-state workflow for coordinating file-backed development work. One durable work item maps to one Dev Orchestrator task, private work proceeds without shared-file ownership, integration and backlog updates use short exact claims, and the parent keeps the Running queue full without creating wait-only tasks or a second task registry. The same lifecycle also connects project bootstrap, planned design, source-backed documentation, implementation, review, verification, and completion.

Orchestrated Development Loop

Step Owner Transition or gate
Bootstrap, when requested Project Bootstrapper Reuse a valid project-root PROJECT.yaml. When it is absent, stale, or explicitly selected for reconfiguration, Project Configurator must create and validate it before documentation work begins. The persisted hybrid-specifications-and-wiki mode keeps structured specifications authoritative and routes README/wiki navigation and synthesis without relying on conversational state. Whole-project reverse engineering reconciles the exact path inventory, reviews every meaningful module, groups the complete set into reviewed high-level designs, derives reviewed architecture and functional specifications, and verifies README/wiki navigation. Each artifact is judged against source evidence, accepted prerequisites, and its current-pass requirements; documentation acceptance is separate from implementation readiness, so an accurate artifact can pass while a documented limitation blocks affected downstream work. After every bottom-up level exists, a supplemental top-down semantic reconciliation checks wiki and functional specifications through architecture, high-level designs, module designs, and source. Corrections belong to the lowest non-conforming documentation layer, propagate upward, and receive fresh review. The reconciliation supplements the bottom-up stop gates and completes reverse engineering without reversing the authoring order.
Intake Dev Backlog Coordinator, Dev Backlog Steward, and Dev Orchestrator Dev Backlog Coordinator counts file-backed Running items and dispatches eligible Ready work until ten are Running or no eligible item remains. Dev Backlog Steward uses a short backlog-only transaction to record the canonical task id, branch, worktree, and initial phase. One user-visible Dev Orchestrator task then owns the item through delivery or a truthful terminal outcome.
Private delivery Dev Orchestrator and selected implementation or writing agents Implementation, correction, read-only review, and focused local tests occur on the task-owned private branch and worktree. They need no project-file claim when they cannot mutate shared state. A claim is required only for main integration, backlog mutation, generated shared output, or a named exclusive resource such as a browser, port, database, or live test facility.
Placement, when needed Project Organiser A new artifact proceeds only after its repository path is approved.
Execution Selected implementation or writing agent The selected agent implements one bounded responsibility and returns a committed, clean handoff before independent review. The generated catalog owns each conceptual agent definition's detailed inputs, skills, and output contract.
Independent contribution review Dev Code Reviewer for source changes; task-selected independent artifact or domain reviewers for setup, documentation, and wiki changes Every changed surface goes to its appropriate reviewer in a fresh read-only context. Source changes go to Dev Code Reviewer; non-source setup, documentation, and wiki artifacts go to their task-selected independent artifact or domain reviewers. A reviewer accepts the contribution or returns correctable findings to the original executor. A correction re-enters fresh review within the bounded correction loop; after all applicable contribution-review gates pass, the accepted lane advances to Dev Verifier.
Contribution verification Dev Verifier The acceptance checks required by the behavior and risk must pass without weakened gates. A failed behavior check returns to the original executor; an accepted lane advances to the path decision.
Delivery-path decision Dev Orchestrator For direct-main delivery, the same Dev Orchestrator that knows the accepted commit and affected paths owns integration and focused post-integration verification. A work item with several accepted committed contributions or an integration conflict uses Dev Merge Coordinator as a nested dependency inside that same canonical task, not as a separate integration task or queue. For pull-request delivery, the authorized reviewer or merge owner performs the merge and the Dev Orchestrator does not acquire a duplicate main-integration claim.
Direct-main integration Dev Orchestrator Acquire one exact claim for every main path the integration may modify, the target integration resource, and only the shared test resources needed for focused verification. Under that ownership, refresh current main and create a fresh reconciliation branch from that exact commit; this becomes the task integration and cleanup branch. Apply only accepted file content or explicitly selected in-scope commits, record prior candidate identifiers and paths durably as source provenance, integrate the bounded result, run focused checks, and release from clean main. Do not import unrelated ancestry merely for provenance or leave a reviewed commit for a separate integration task.
Multi-contribution reconciliation, when required Dev Orchestrator and nested Dev Merge Coordinator Within the same work item and canonical task, combine the accepted commits in dependency order, preserve each contribution's provenance, and resolve integration-only conflicts. Then send every changed surface through the applicable fresh independent review before Dev Verifier checks the complete integrated result. This conditional dependency does not create another user-visible task, queue, ledger, or ownership chain.
Focused verification Dev Orchestrator and Dev Verifier Per-item verification is proportional to the affected surface and risk. Start with changed-module and directly related regressions; add freshness, shared-resource, or integration checks only when those surfaces require them. Expand after a focused failure or evidence-backed cross-cutting risk. The complete agent catalog runs once against the final integrated campaign state, not once per work item.
Correction or blocker Original executor and Dev Orchestrator Findings return to the original executor and corrected work re-enters fresh review and focused verification. Expensive failures are classified from retained evidence before another live or broad run. After two failed correction attempts for the same criterion, a repeated failure signature, or an unavailable fixed dependency, Dev Orchestrator records the preserved commit and exact blocker instead of substituting self-review or another blind retry.
Completion and cleanup Dev Orchestrator, Dev Backlog Steward, and Dev Backlog Coordinator After integration ownership is released, use a separate short claim for exactly the active work-item path and completed destination. Record delivery evidence, set Status: Completed, archive the item, commit, and release. The parent verifies that the fresh task integration branch is fully merged, removes its clean worktree, safely deletes that merged branch, prunes metadata, sets Done — item, archives the task, recounts Running items, and fills the vacancy. Any older candidate branch retained only as a non-ancestral content source is handled separately under repository cleanup policy after its durable mapping and lack of unique work are confirmed.

Claims, Worktrees, And Communication

The durable work item, Git history, coordination registry, and Codex task each answer a different question. Keeping those responsibilities separate removes the need for baton ledgers, waiting-task registries, and separate integration queues.

Planned Design Progression

Normal development uses the shared production skills from accepted functional intent down to verified code. Project-specific evaluation harnesses may compare frozen outputs afterward, but hidden reference artifacts, evaluator rubrics, and an original implementation do not enter production generation.

Stage Production input and owner Acceptance gate
Functional intent Accepted functional specifications and architecture define required outcomes, actors, permissions, workflows, constraints, and system boundaries. Every applicable requirement has stable authority or is explicitly open before subsystem design begins. A primary and supporting operation inventory preserves every directly invoked route, API, command, event, job, notification, and reference-data lookup with its observable access, selector, paging, projection, response, error, state, and verification contract.
High-level design The standard create-high-level-design skill works in PLANNED_DEVELOPMENT mode; review-high-level-design independently checks the result. Requirements coverage, critical trust and identity boundaries, and cross-module contracts pass review. A source-category inventory, operation-and-obligation inventory, and boundary-edge inventory close before prose so scheduled work, source open questions, caches, privileged tasks, and every producer-consumer edge remain visible. Each exact method, route variant, supporting UI action, command, event, or job identity remains one-to-one operation-level coverage; an abstract group cannot replace it. Each applicable anonymous, authenticated, administrator, service, or background actor receives an explicit boundary row, including denial or equivalent-role behavior. Local links resolve from the installed documentation path and never cite transient assembly or control files. An unresolved high-impact actor, authority, selector, disclosure, validation, state, transaction, asynchronous, or error-timing contract blocks downstream module design.
Module design The standard create-module-design skill consumes the accepted functional and HLD inputs; review-module-design independently checks the result. The candidate first passes an exact ordered template-heading and decision-marker gate; missing, renamed, duplicated, merged, or reordered mandatory sections, a Documentation Acceptance section that does not begin with ACCEPTED or BLOCKED, or an Implementation Readiness section that does not begin with READY or BLOCKED stops the candidate before semantic review. Local links resolve from the installed documentation path and never cite transient assembly or control files. A source-category inventory and owning-HLD open-question handoff close before prose. Every applicable requirement then maps to an implementable contract, rule, state, error path, and verification obligation. Scope-bearing qualifiers from the target assignment and owning-HLD component description remain explicit operation facets rather than being shortened to a generic module label. Compatible facts from accepted inputs are reconciled for the same exact operation without borrowing sibling contracts. Identity selectors, validation ownership, response disclosure, returned or emitted values, persistent state and cache mutations, side-effect phase ownership, failure timing, and sensitive logging are explicit and internally consistent. Executor acceptance precedes executor-owned work, while separately supported initiator precomputation and later sender or provider rejection remain distinct. Labels such as public do not substitute for operation-specific authentication evidence.
Implementation Dev Orchestrator delegates the normalized work item and selected work-item process to Dev Coder. The coder implements the accepted design with the technology skills already routed for the affected project folders. Implementation does not receive project-specific reconstruction instructions or evaluator guidance. It preserves accepted contracts and supplies tests for the named verification obligations. Direct-main delivery remains with the Dev Orchestrator through accepted integration and focused post-integration verification. Feature-branch delivery ends with a pushed pull request ready for its authorized reviewer or merge owner. Backlog completion is always a separate provider transaction after delivery evidence exists.
Verification and evaluation Normal independent review and verification prove the implementation. A separate project-owned evaluation run may then compare frozen artifacts or observable behavior with hidden references through Deterministic Judges and, only where exact checks are insufficient, a Model Judge. Ordinary synthetic Codex and Junie cases run locally in disposable workspaces with controlled harness state, timeouts, cleanup, isolated evidence, and mutation auditing. Explicitly high-risk cases require the externally-contained tier. Production acceptance remains distinct from comparative scoring. Executed, Judge-passed, Model Judge calibration, security-contained, and stale-by-digest are separate evaluation claims. Deterministic critical gates run first and stop semantic judging when they fail. A canonical Model Judge request binds the selected case, run, harness, candidate-output artifact, and governed evidence artifacts. Model Judge calibration promotion remains disabled until every calibration sample also binds trusted execution identity, independent Human Judge evidence, adjudication where required, and critical-dimension coverage. Hidden references, expected findings, Judge prompts, and calibration answers never enter production generation.

Execution Evidence

An orchestrated run leaves complementary records with deliberately separate responsibilities. No title, message, claim event, or branch label can substitute for the evidence owned by another record.

Record Owns Does not own
File-backed work item Lifecycle state, canonical task id, branch and worktree, current phase, waits, open issues, accepted commit, review, verification, integration, completion, and cleanup evidence. Git reachability, live shared ownership, or task UI state.
Git Source and integration commits, branch ancestry or recorded non-ancestral mapping, changed paths, clean status, and safe worktree or branch cleanup eligibility. Review acceptance, test meaning, or work-item lifecycle.
Review and verification outputs The exact candidate, findings or acceptance, checks run, retained reports, risks, cleanup observations, and justified omissions. Shared mutation ownership or terminal backlog state.
Coordination registry and event journal Current exact shared ownership, contention, heartbeat, release, and recovery observations. Whether committed paths or product bytes were accepted, correctly integrated, delivered, or completed.
Codex task Live execution, concise phase title, messages, and user-visible status. Durable identity, work-item lifecycle, Git delivery, or claim authority.
