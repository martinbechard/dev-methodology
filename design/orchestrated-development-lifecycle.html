A practical operating model for many agents and one codebase

Orchestrated Development Lifecycle

Work moves through one selected-Persistence queue when a provider is selected, or through task-local result evidence when provider none applies. Each item uses one bounded delivery lane and short coordination gates only when agents must touch the same shared object.

Methodology installation first chooses and records core-skill delivery while producing and installing matching generated Agent configurations. Later project setup reuses that evidence, creates PROJECT.yaml and only the selected empty wiki or specification roots, and does not run reverse engineering. Explicit later documentation and development workflows consume the accepted configuration and routed skill references.

Work-Item Continuity

The work item's status, decisions, owner, accepted change, verification, and delivery evidence travel together from intake to completion.

Chapter 01

Work-Item Backlog

Selected Persistence separates what the work is from where it happens. A work item is classified by outcome, then moved through a small set of explicit states. Provider none keeps equivalent task-local result evidence without inventing a provider queue.

Work-Item Types

Feature
Add or expand a capability.
Defect
Correct broken or regressed behavior.
Analysis
Produce an evidence-backed answer or recommendation.
Investigation
Trace an unclear failure or risk until the next action is known.

Work-Item Readiness

Clear outcome
Requirements and acceptance criteria are observable.
Known authority
Approvals and user-owned decisions are recorded.
Dependencies
Required predecessors are complete or explicitly absent.
Verification
The item says how completion will be demonstrated.
Chapter 02

File-Backed Work Items

A file provider stores each work item as Markdown in the repository. The file is readable in review, versioned with the project, and sufficient for a future agent to continue without the original conversation.

When Persistence is selected, the Work-item content is the Work-item authority and is stored according to the Persistence provider's specific format. File-provider creation and lifecycle procedures are defined by Create Work Item File and Manage File Work Items.

New Work-Item Discovery

After a new work item is persisted, the creator sends no routine task message. The Coordinator discovers it through the authoritative provider inventory when scheduling or reconciling capacity.

A creator contacts the Coordinator only for a specific decision it cannot resolve. The message does not duplicate durable creation evidence or start implementation.

Chapter 03

Agent Roles

A Role is a reusable responsibility and authority contract applied to a runtime Agent; each Agent below owns one distinct kind of decision.

Execution Contexts

Each scheduled Dispatcher cycle uses a fresh disposable task. It reads current provider and runtime state, obtains one Coordinator decision, performs the authorized runtime operation, reports the result during the same run, and archives itself.

After one Work Item is selected, that disposable run retitles itself Dispatch followed by the short Work Item title. The launched Work-Item task continues independently after its Dispatcher run archives itself.

A later Dispatcher run resumes a non-archived canonical Work-Item task by sending one authorized follow-up to its exact task identity. If that canonical task is archived, the Coordinator authorizes one successor, the Dispatcher creates it once, and the Work-item provider durably transfers runtime ownership before the successor accepts Running. The archived identity remains predecessor provenance.

Runtime Parent Task ID is provenance and ambiguous-creation evidence, not a callback address.

The Dev Backlog Watchdog runs as a standalone project automation outside Dispatcher and Work-Item tasks and outside delivery capacity. Each schedule creates a fresh read-only task. A healthy run archives itself; an actionable or failed run remains visible.

Dev Backlog Steward is optional and limited to provider-wide inventory, normalization, archival audits, and recovery. The authorized Coordinator or Orchestrator directly applies ordinary lifecycle operations through the selected manager.

An Assignment is bounded work sent to an Agent; it does not create another work-item execution. A runtime may retain a child execution context for that Agent, but the methodology still treats it as part of the owning Dispatcher run or Work-Item execution.

The development-agent catalog owns the complete Role definitions. Coordinate Work Items owns portable queue policy. Coordinate Codex Tasks owns the conditional runtime mapping.

Chapter 04

Runtime Coordination

Runtime Coordination Surfaces

The shared coordinate-work-items skill is the single normative authority for lifecycle, active-execution eligibility, capacity, scheduling, recovery, delivery, and reporting. Dev Backlog Coordinator, Dev Backlog Steward, Dev Orchestrator, and Dev Backlog Watchdog select that portable policy for their applicable responsibilities. The provider manager remains atomic and does not own runtime state.

When executions use Codex tasks, coordinate-codex-tasks supplies capability, creation, resumption, identity, title, follow-up, reconciliation, Watchdog-task, and archival mappings. For this repository, Backlog Dispatcher specializes Watchdog scheduling as one standalone project automation that creates a fresh task per run instead of waking the retained Dispatcher conversation. The stable task and conversation identities remain distinct from display text. Neither peer duplicates the other peer's authority.

Backlog Blockage Recovery And Dispatch Mode

Coordinator inventory reconciliation, the user, or the Watchdog may declare a backlog blockage when the documented conditions apply. Resolve Backlog Blockage owns one-item-at-a-time recovery and diagnosis. The Coordinator remains the dispatcher while exactly one separate canonical work-item task performs delivery without claims and every other mutating execution stays paused.

At crisis entry, preserve the commits, diffs, candidates, worktrees, reviews, verification, and blocker evidence for every paused mutator. After preservation is verified, reset the configured claim registry exactly once. Perform no further claim operation until crisis exit restores ordinary coordination, and do not reconstruct crisis-era claims.

When a secondary-task dispatch mechanism exists, Set Solo Mode disables parallel dispatch while retaining serial dispatch of one task. Set Multitask Mode restores parallel dispatch only after every blockage item is terminal, no Blocked item or mutator remains active, all recovery changes are committed, and required verification has a concrete disposition.

Repeated transitions preserve the effective setting. Recovery proceeds without either mode skill when no secondary-task dispatch mechanism exists.

Chapter 05

Bounded Workspaces

A work item can use a separate branch or worktree when the selected delivery route needs isolated source work. Files, outputs, and caches remain separate until delivery for that route.

Chapter 06

Shared-Resource Coordination

Resource Claim applies only when a valid PROJECT.yaml explicitly selects it. With no PROJECT.yaml or a selected value of none, agents leave the helper and claim state untouched. An invalid PROJECT.yaml stops with its validation failure before helper or claim-state access. The claim registry records temporary ownership; it does not prove review, delivery, or completion.

Claim Cleanup

Release removes the named live claim while the registry is locked and records a RELEASED event. It does not inspect Git state or decide whether delivery completed. Ordinary restarts reconcile through the configured helper. Reset belongs only to the declared backlog-crisis entry path.

Claim Limits

A claim records temporary ownership. Use activity work for outcome work and activity update for provider mutation. Work-item claims use the exact opaque Work Item ID. Path and resource claims can also apply independently.

When shared files or resources are in scope, request the smallest currently known exact path or resource manifest; do not request the whole project for a fixed subset. Review, verification, Git delivery, and work-item completion require separate evidence.

Resource Claim is the only source for claim events, scopes, conflicts, deadlines, recovery, and release timing. Resource Claim Helper owns the common helper contract. Resource Claim Helper Command and Resource Claim Helper MCP describe only how to invoke that contract.

Chapter 07

Delivery Stages

Production work is accepted in layers. Review asks whether the change is correct and maintainable; verification proves the required behavior; delivery integrates the accepted result through the configured path.

Main-branch delivery

  1. Review and verify the accepted candidate.
  2. Follow Resource Claim when its Claim Events table applies.
  3. Apply the Commit-selected main-branch contract and preserve evidence for the exact integration base and checkout.
  4. If current source contracts disagree about the integration branch or checkout shape, stop for source-contract disposition instead of choosing silently.
  5. Apply only accepted paths, verify the integrated result, update main, and complete delivery closeout with clean-state evidence or preserved-unrelated-dirt evidence and no integration residue.

Feature-branch delivery

  1. Review and verify the feature branch.
  2. The Commit skill publishes a GitHub pull request or GitLab merge request and returns Commit AWAITING_REVIEW without Persistence mutation.
  3. Dev Orchestrator directly applies the effective Persistence manager exactly once for the nonterminal AWAITING_REVIEW update; repeated observation reconciles that update.
  4. Resume the same delivery identity through provider-accurate review, checks, merge, and main observation until Commit READY, then directly apply the manager exactly once for the distinct terminal Persistence closure. Provider none keeps both states task-local.
Integration Cleanup

Use the integration and cleanup checkout required by the effective Commit source. When source contracts conflict about that checkout, record the limitation and request disposition rather than inferring a replacement contract.

Before handoff, commit completed work and prove either the required clean state or preserved unrelated dirt with no integration residue. The Dev Orchestrator returns that evidence without cleaning up its own active execution. The Coordinator decides whether the gates pass, and the root Dispatcher executes only the exact authorized cleanup packet.

The provider-neutral contract is defined by Deliver Work Item. Provider details are defined by Deliver Work Item Main Branch, Deliver Work Item Feature Branch, and Create Pull Request.

Chapter 08

Blocker Recovery

Known Blocker Handoff

Orchestrator Blocker Steps

  1. Stop unsafe work.
  2. Preserve commits and evidence.
  3. Resolve resource ownership truthfully.
  4. Notify the Coordinator immediately.

Blocker Notification Fields

Cause
Exact blocker and owner.
Exit
Observable unblock condition and requested action.
Identity
Canonical runtime execution identity. When coordinate-codex-tasks is active, include its distinct task and conversation identities.
Resume
Whether resumption is safe.

Coordinator Sequence

  1. Acknowledge and reconcile the complete handoff.
  2. After exhausted corrections, return exactly one immutable decision: a recovery with evidence linked to every finding, one similarly linked bounded retry, one explained genuine user decision with options and tradeoffs, or one continuing external or technical dependency with an observable trigger.
  3. Reject indefinite Blocked. For selected Persistence, directly apply the authorized provider mutation through the effective manager. With provider none, retain the equivalent task-local result evidence. Consume a bounded retry before reconciling again, and do not repeat it.
Execution Safeguards

Findings return to the same producing responsibility through a new fresh-context Agent. Each collaboration Agent gets one execution turn; after it returns, its identity is not reused. The next Agent receives a compact handoff that references the authoritative Work Item, candidate commit, and relevant durable evidence instead of the prior conversation. Count the initial failed review as the first failure and allow at most two corrected resubmissions. Third failed review: preserve the canonical execution, candidate, review, verification, Git, claim, and attempt history, stop the loop, and notify the parent Coordinator. The Coordinator records User Action Required before asking one concrete user decision; no fourth review cycle begins. When coordinate-codex-tasks is active, also preserve its canonical task and conversation identities.

Before a phase expected to exceed five minutes, record the active unit, estimate, hard stop, retained evidence path, and distinct acceptance criterion locally. Do not send a routine progress message. After an expensive failure, classify retained evidence, add the smallest offline regression, and run one cheapest representative first.

Chapter 09

User Decision Gates

Agents resolve technical questions from evidence. A work item moves to User Action Required only when the next safe step depends on authority, intent, risk acceptance, or information that belongs to the user.

Coordinator inability alone does not manufacture a user obligation. A technical or external cause remains Blocked with an exact owner and observable unblock condition until one concrete action genuinely belongs to the user.

1 · Recorded State

The Coordinator selects User Action Required. For selected Persistence, the selected Persistence manager stores it before the request is presented. With provider none, retain the question and state in task-local result evidence.

2 · Clear Question

Ask one plain-language question and explain why the user owns the answer.

3 · Consequences And Boundary

Give evidence-backed options or an illustrative example. State each consequence and exactly what unattended work stops.

4 · Decision Record

Store the exact answer, date, provenance, approved scope, and exclusions.

5 · Same-Execution Resume

For selected Persistence, the Coordinator serializes User Action Required to Ready, then Ready to Starting, through the selected manager. With provider none, the same state evidence stays task-local. The same root Orchestrator directly records Starting to Running. When coordinate-codex-tasks is active, retain the same task and conversation identities.

The same root Orchestrator resumes the existing execution; no replacement is created. The user does not need to repeat the answer in the parent coordination context. A user answer resolves the decision gate, not delivery. Work produced before reconciliation is preserved for ownership, scope, review, verification, and delivery checks. Execution context alone never invalidates it.

Chapter 11

Design And Documentation Workflows

Design and documentation change the producer and reviewer, not the lifecycle. They still start from an authorized work item or an explicit provider-none task, proceed in a bounded lane, receive independent review, pass focused verification, and use the configured delivery path.

Functional specification

Actors, outcomes, permissions, workflows, and constraints.

Architecture

System boundaries, trust, dependencies, and cross-cutting decisions.

High-level design

Feature families, modules, interactions, and implementation order.

Module design

Implementable contracts, states, failure behavior, and verification obligations.

Implementation

Code and tests preserve the accepted design through review and verification.

Planned Development

Accepted functional specifications and architecture are upstream authority. Create and review high-level and module designs before dependent implementation.

Unless the user explicitly directs coding without planning, Dev Coder prepares a bounded implementation and TDD plan. Dev Architect reviews assignment alignment, requirements traceability, mature-software reuse, the smallest viable approach, and proportionality before coding. A methodology artifact may receive a separate optional methodology-conformance review.

Accepted plans enter coding. Correctable plans return to Dev Coder.

An explicitly approved material-infrastructure outcome can proceed when the original user request includes that exact outcome or a later recorded User Action Required answer explicitly approves it.

Without either approval source, preserve the proposal and route exactly one contextual User Action Required question that identifies the infrastructure, explains the approval need, gives concrete options and practical tradeoffs, and asks for one decision. Infrastructure implementation remains unauthorized until the user answers.

Ordinary tests and routine fixtures remain inside coding. Substantial custom test infrastructure returns to the planning gate before implementation.

Documentation acceptance and implementation readiness are separate decisions: an accurate document may be accepted while an unresolved high-impact contract blocks downstream work.

Whole-Project Reverse Engineering

The persisted hybrid-specifications-and-wiki mode keeps structured specifications authoritative. Work proceeds bottom-up from source and module evidence, then performs a final top-down semantic reconciliation through wiki, functional specifications, architecture, high-level designs, module designs, and source.
